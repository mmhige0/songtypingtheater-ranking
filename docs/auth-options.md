# 個別トークンの初回登録・復旧検討

更新日: 2026-10-11（日本時間）

## 採用済みの方針

提示されたゲーム側v1の個別installationToken方式を採用する。サーバーがtokenを発行し、ゲームが保存してBearer認証に使う。
共通登録キー方式は採用しない。tokenの平文は通常の認証DBには保存せず、ハッシュと失効状態を保存する。
匿名登録は正規ゲーム・本人の証明ではなく、送信元ごとの制限・失効に使う。本格的なスコア改ざん対策は後回し。

## 解決すべき問題

登録が成功した後に応答が失われると、ゲームにtokenが残らない。
現在の「同じplayerIdは409、IDだけでは再発行しない」は不正な再発行を防ぐ一方、この通信失敗から復旧できない。
IDだけを提示して再発行する方法は採用しない。

## 復旧案: 事前保存した登録用秘密で期間限定再取得

以下は検討案。ゲーム側v1への追加項目・期間について最終調整が必要。

1. ゲームはplayerIdと暗号学的乱数のregistrationSecret（32バイト）を生成し、APIを呼ぶ前に永続保存する。
2. POST /api/v1/installationsにplayerIdとregistrationSecretを送る。
3. APIはplayerIdとregistrationSecretのハッシュを一意制約付きで保存し、installationTokenを発行する。
4. 通常の認証DBにはtokenのハッシュだけ保存する。復旧用にtokenをサーバー側の専用鍵で暗号化して一時保存する。
5. 同じplayerId・同じregistrationSecretで再試行した場合、期限内なら同じtokenを返す。秘密が異なる場合は409とし、既存の認証情報を変更しない。
6. ゲームは受け取ったtokenを永続保存してから通常の成績送信を開始する。
7. 暗号化した復旧用tokenは発行から7日で削除する初期案。期間はゲーム側と調整する。

本文案:
`{"playerId":"<UUIDv4>","registrationSecret":"<32バイトのbase64url・パディングなし43文字>"}`

新規は201、期間内の同じ登録の再試行は200。どちらもplayerIdとinstallationTokenを返し、Cache-Control: no-storeを指定する。
一意制約の競合で同時登録が起きても、同じ秘密なら同じtoken、異なる秘密なら409とする。
発行・ハッシュ・復旧データは一つのトランザクションで保存する。初回成功後の再試行で別tokenを生成しない。
registrationSecret自体をtokenにせず、成績送信にはサーバー発行のinstallationTokenだけを使う。

## 異常時・秘密情報

- 同じIDで異なる登録用秘密: 409 PLAYER_ID_ALREADY_REGISTERED。
- 同じ秘密だが復旧期限切れ: 409 REGISTRATION_RECOVERY_EXPIRED。IDだけでtokenを再発行しない。
- 失効済みtoken: 401 REVOKED_TOKEN。登録再送で再有効化しない。
- playerIdだけ残り秘密やtokenが消失: 自動復旧できない。本人確認付き復旧か新IDへの移行は別途決める。
- 復旧用の暗号鍵はソースやDBと分離した秘密設定で管理。復旧データの削除と鍵更新の運用が必要。
- registrationSecret・token・認証ヘッダー・登録本文をログに出さない。
- ゲームはplayerIdと登録用秘密をネットワーク送信前に永続化する。token保存後も、再取得が必要な期間は秘密を保持する。
- セーブ複製はID・tokenも複製する。別PC利用と本人の厳密な区別は保証しない。
- 公開されたplayerIdの事前登録による占有を減らすため、登録完了後にPhotonへ公開する案をゲーム側と調整する。Photonの運用自体はWeb側の責務ではない。

## 他案との比較

クライアントが送信用tokenそのものを事前生成すれば、サーバーはハッシュだけで同じ登録を確認でき、復旧データの暗号化保存が不要になる。
ただし「サーバーがtokenを発行する」契約が変わるため、今回は採用済みとは扱わない。

## 確認が必要な点

- registrationSecretの追加と事前永続保存への対応。
- 復旧データの7日保持、期限切れ・セーブ消失時の運用。
- サーバー発行方式で復旧データの暗号化保存を許容するか。通常の認証DBはtokenハッシュだけだが、復旧のために暗号化したtokenを一時保持する変更となる。

これらが合意されるまでは初回登録処理を最終契約として固定しない。匿名トークン方式の採用自体は確定。
