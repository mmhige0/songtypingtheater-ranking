# 決定事項・未決定事項

更新日: 2026-10-11（日本時間）

## 確定

- 曲ID×人数でランキングを分け、メンバーの組み合わせごとの最高記録を表示。
- 集計用のteamKeyをPlayの列として保存。Web側で参加者IDを正規化・ソートし、空白なしJSON配列文字列として生成する。
- 旧記録の達成日時を保存する列は設けない。移行分のreceivedAtはインポート受付時刻とする。
- 同じ組み合わせの同点はFC優先を維持する。異なるチーム同点は競技順位（1、1、3）。
- FC印は代表プレイ自身の値。過去の不明を未達成にしない。
- 別譜面は別曲ID。同じ曲IDの修正前後・ゲームバージョン違いは分離しない。
- Unity/C#のホストからHTTPSでJSONを送信。全参加者のIDを送信。
- プレイヤーIDはセーブデータに保存。提示v1を基にplayerId/playIdはUUIDv4とする設計。
- 認証はクライアント生成の個別installationToken方式で合意。ゲーム側がRandomNumberGeneratorで32バイトを生成し、Base64URL（パディングなし43文字）にしてplayerIdとともに通信前に永続保存する。ホストがBearer認証で送る。共通登録キー方式は採用しない。
- 登録は新規201、同一ID・同一token再送200、同一ID・異なるtoken409、失効済みの同一token401。別IDで同じtokenは409。上書き・再有効化しない。成功応答にtokenは含めない。
- tokenはSHA-256ハッシュのみ保存。復旧用暗号化token・登録用秘密・暗号鍵管理・7日削除ジョブは不要。通信失敗・5xxは同じ値で再送し、429はRetry-Afterに従う。詳細は[初回登録・再送仕様](auth-options.md)。
- TAIPEN ONかつ4人の記録は残す。ONかつ1〜3人は拒否。
- 通常とサバイバルを分けない。対戦・Debug等の送信抑止はゲーム側。
- PhotonのMaster Client交代・参加者スナップショット管理はゲーム側の責務。Web側でPhoton固有の処理は実装しない。
- 新規APIで全受理プレイを保存。playId一意制約とトランザクションで同時再送も重複防止。
- 失敗成績・失敗履歴は保存しない。成功済みの履歴と未送信の一時キューは別。
- colorはR/B/Y/Gの大文字のみ。小文字を正規化して受け付けない。
- 本格的なスコア改ざん対策は初期範囲外。個別トークンは正規プレイの証明ではない。

- v1はfinishedAtを送らずreceivedAtで先着判定。これは達成順から受付順への変更。
- gameVersionをv1新規送信では必須に変更。移行分の不明は許容。
- 再送キューは最大100件・初回保存から7日。期限切れ・非再送エラーは破棄、失敗履歴なし。
- 曲マスター登録完了後にゲームへ新曲を公開する。未登録曲は従来どおり非再送エラー。
- ホストを含む全参加者の初回登録完了を成績送信条件とする。未登録参加者は422 UNKNOWN_PLAYERとし、受付時の自動登録は行わない。
- 名前検索は代表記録選択後のnameAtPlayだけを対象にする。最新名や別記録の名前では検索しない。
- 移行元は現在のシートのみ。他の元データ・ログは残っていない。曲・人数・名前の組み合わせ（順不同・完全一致）で最高スコアのみ移行する。
- 旧記録は内部専用IDで管理し、新playerIdへ自動紐付けしない。確認済み対応だけを反映する。日時・FC等の不明情報は補完しない。
- 実プレイヤー名・個別成績・対応表はGit・PR・Issue・AIの作業メモリやログに残さない。設計・テストには架空データだけを用いる。

- 曲マスターの正本はランキングDB。Songは内部IDを主キーとし、gameSongIdはnull許容の一意列、statusを持つ。v1ではapprovedの曲だけを作成する。
- v1の曲登録は管理者のみ。管理用キー（Bearer）で認証するPUT /api/v1/admin/songs/{gameSongId}と登録スクリプトで行い、管理画面は後回し。
- 曲一覧シートの曲番はgameSongIdと同じ。シートは移行完了後に廃止し、移行時に曲マスターを一度だけ初期登録する。
- 同期方向はランキング→LyricDataCreatorの一方向（公開曲一覧APIを利用）。譜面・YouTube URLはランキングに保存しない。
- levelSortValueはLyricDataCreatorと同じ算出式（整数部×3、+は+1、-は-1）。難易度は数値形式のほか`-`（未定）・`?`（不明）も受理し、文字列のまま保存する。この2つとnullのlevelSortValueはnull。
- 譜面投稿フロー（投稿→未承認曲として仮登録→承認・本登録）は将来構想。v1には入れない。

- 構成はCloudflare無料プラン（Workers＋Hono、D1、Drizzle）。比較検討は行わない。詳細は[システム構成](architecture.md)。
- 送信回数制限はAPI仕様の値に厳密には従わず、Workers Rate Limitingで設定できる期間・回数に合わせる。
- 同じplayIdの成績再送は本文を比較せず一律200 already_registered（初回receivedAtを返す）。409 PLAY_ID_CONFLICTと比較用の元の登録値の保持は廃止。ゲーム側の対応変更は不要。
- 移行元の行識別子（legacyRecordKey）とPlay.sourceは持たない。hostPlayerIdがnullの記録を移行分とみなす。公開前は移行分を全削除して取り込み直せ、公開後は取り込み直さない。
- 移行用playerIdは`legacy-`で始まる形式。Playerに種別の列は設けない。
- 送信tokenのハッシュ・失効はPlayerの列とし、Installationテーブルは設けない（1プレイヤー1token）。
- 参加者の表示順は色のR→B→Y→G。同じプレイ内の色の重複は400 DUPLICATE_COLOR。受信順は保存しない。移行分はシート上の並び順にR・B・Y・Gを仮に割り当てる。
- 曲番号順は`CAST(game_song_id AS INTEGER), game_song_id`で並べ、索引で全件走査を避ける（4桁以上の曲番に対応）。

## 設計案として反映（最終調整）

- レート制限の初期値はplaysがIP・installationそれぞれ60秒20リクエスト、installationsはIP60秒5リクエスト、曲登録APIは制限なし。運用設定として実測後に調整。
- フル絞り込みでは全受理記録のFC記録から代表を選ぶ。
- FC不明と未達成は同点の代表選択で同じ優先度とする。
